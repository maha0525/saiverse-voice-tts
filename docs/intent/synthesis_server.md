# Intent: ローカルと外部で同じ音声合成を使う

**ステータス**: 検証待ち (実機のサーバーの入れ替えと、見本の声での合成の確認まで済み。ペルソナの声を人の耳で聞く確認が残っている)

## 要点

声を作る処理を一つにまとめる。同じ PC で使うときは、Voice TTS が起動する子プロセスの中でその処理を動かす (今と同じ)。別の PC で使うときは、その PC で同じ処理を音声合成サーバーとして動かし、ネットワーク越しに合成の依頼を受け付ける。どちらにも同じ合成の依頼 (文章・参照音声・書き起こし・話速などの調整値) を渡し、どちらからも同じ形式で声が断片ごとに返ってくる。違うのは、つなぎ方と、参照音声を渡す方法だけになる。

## なぜやるか

外部 GPT-SoVITS サーバー (docs/intent/remote_gpt_sovits.md) を入れた時点で、ローカル合成と外部サーバーの間に三つの差が残った。

1. **調整値が効かない。** 外部サーバーには文章とプロファイル ID しか送っていないので、ペルソナ別に設定した話速・top_k などが外部サーバーでは無視される。
2. **最初の声が遅い。** ローカル合成では、声ができた断片から順に再生を始める。外部サーバーでは、一文の声が全部できるまで何も返ってこない。
3. **サーバーのプログラムが Voice TTS の外にある。** 今動いている外部サーバーは、GPU 機に置いた単独のスクリプトで、Voice TTS のエンジンのコードを手で写したものを使っている。公開されていないので、他の利用者は URL 欄に入れる接続先を用意できない。手で写したコードなので、Voice TTS 側を直しても追従しない。

ほかに、参照音声の形式の差もある。設定画面では mp3 / flac / ogg も選べるが、今の外部サーバーは WAV にしか対応していないので、WAV 以外を設定したペルソナは外部サーバーでは声が出ない。

三つの差の原因は同じで、外部サーバーがローカル合成とは別の処理になっていることにある。ローカルの子プロセスでは、もともと「合成の依頼を受けて、エンジンを回して、声を断片ごとに返す」流れになっている。この流れをそのままネットワーク越しにも使えるようにすれば、三つの差は同時に消える。

## 利用者から見て変わること

- 外部サーバーでも、ペルソナ別の話速などの調整が効く。
- 外部サーバーでも、ローカルと同じように、声ができた断片から再生が始まる。
- Voice TTS を入れた GPU 機で起動スクリプトを一つ実行すれば、その機械が音声合成サーバーになる。別のプログラムを探して入れる必要は無い。
- 参照音声が mp3 / flac / ogg のペルソナも、外部サーバーで声が出る。
- ローカル合成の使い勝手は何も変わらない。

## 入力から再生まで

```
            ┌─ 同じ PC ──── 子プロセス (標準入出力でつなぐ) ─┐
playback_worker                                                  ├─ 共通の合成関数 ─ エンジン (GPT-SoVITS)
            └─ 別の PC ──── 音声合成サーバー (HTTP でつなぐ) ─┘
```

1. playback_worker がペルソナの設定から、文章・参照音声・書き起こし・調整値を集める (今と同じ)。
2. URL が空ならローカルの子プロセスへ、URL があれば外部サーバーへ合成を依頼する (今と同じ分かれ方)。
3. 外部サーバーへ依頼するときは、参照音声をペルソナ ID のプロファイルとしてサーバーに登録してから依頼する。登録し直す条件は remote_gpt_sovits.md のとおりで、サーバーの登録を手元の設定に合わせる。
4. 子プロセスもサーバーも、受けた依頼を共通の合成関数に渡す。共通の合成関数の中でエンジンを回し、できた声を断片ごとに順に返す。
5. 子プロセスは声の断片を標準出力へ、サーバーは HTTP の応答本文へ、同じ形式 (一つ一つのデータの先頭にそのデータの長さを付けた形式。subprocess_ipc で決めている) で流す。受け取る側は同じ読み方で断片を取り出し、今と同じ連結・保存・配信に乗せる。

## 決めること

### 共通の合成関数

subprocess_worker の中の「依頼を一つ受けて、エンジンを回して、声の断片を返す」部分を関数として切り出し、子プロセスとサーバーの両方からその関数を呼ぶ。関数は書き出し先を持たず、送るべきフレームを順に返す (子プロセスは標準出力へ、サーバーは HTTP の応答へ書く)。エンジンの準備 (GPT-SoVITS / Irodori-TTS の選択と設定) も同じ場所で行う。子プロセスだけに必要な部分 (標準入出力の扱い、標準出力の向き先の切り替え) は今のまま子プロセスに残す。

エンジンの設定 (言語・デバイスなど) は、子プロセスと同じく Voice TTS の `config/default.json` の `engines.<エンジン名>` から読む。外部サーバーでは、サーバーの機械の設定ファイルが使われる。言語はペルソナごとの調整値ではなく機械ごとの設定なので、手元とサーバーで言語の設定がずれていれば声もずれる。README にそう書く。

### 音声合成サーバーとのやり取り

今のやり取りの形は全部そのまま受け付け、足すだけにする。以下、今のやり取りの形だけを使うクライアント (文章とプロファイル ID だけを送り、WAV を一括で受け取るもの) を「従来のクライアント」と呼ぶ。

- `GET /health` → `{"ok": true, "model_loaded": bool, "device": "...", "engine": "gpt_sovits", "protocol": 2}`。今の三つの項目は残し、`engine` と `protocol` を足す。`protocol` が 2 以上なら、下の拡張に対応したサーバーである。
- `GET /profiles/{id}` → `{"exists": true, "ref_text": "..."}` または 404 (今と同じ)。
- `PUT /profiles/{id}` (multipart: `ref_audio` + `ref_text`) → `{"ok": true}`。参照音声は WAV に限らず、soundfile で読める形式を受け付ける (この機械の soundfile 0.14.0 / libsndfile 1.2.2 で mp3 が読めることは確かめた。Linux と Mac の専用環境は未確認)。大きさの上限は設定画面と同じ 50MB。GPT-SoVITS は長さが 3〜10 秒の範囲から外れた参照音声を使うと合成時に失敗するので、登録の時点で長さを確かめて、外れていれば理由を書いて 400 で返す。
- `POST /synthesize` (JSON):
  - `{"profile_id", "text"}` だけなら、今と同じく完成した WAV を一括で返す。
  - `"params": {...}` を付けると、その調整値をエンジンに渡す。付けなければエンジンの既定値になる (今の外部サーバーの固定値と同じ値)。
  - `"stream": true` を付けると、応答本文で声の断片を子プロセスと同じ形式で順に返す。断片を一つも返す前の失敗 (知らないプロファイル、空の文章、モデルの読み込み中) は、HTTP の状態コード (400 / 404 / 503) と JSON の理由で返す。断片を返し始めた後の失敗は、エラーの通知と終了の通知 (この依頼の声はここまで、という印) で返す。成功したときも、最後に終了の通知を返す。

サーバーは起動した時点で裏でモデルを読み込む。読み込み中の合成の依頼には、待たせずに 503 と「モデルを読み込み中」を返す (クライアントのタイムアウトは既定で 15 秒なので、待たせるとどのみち失敗するため)。

サーバーのエンジンは一つだけで、合成は一度に一件ずつ行う (GPU を取り合わない。今のサーバーと同じ)。サーバーは、プロファイルの登録の依頼も合成と同じ順番待ちに並べて、一件ずつ処理する。一件の合成は、始めから終わりまで順番を占める。途中で依頼元が切断したら、サーバーは次の断片を書き出せなかった時点で合成を打ち切り、次の依頼に順番を回す。応答を読まずに接続だけ残す依頼元がいても順番を占め続けないよう、サーバーは一つの断片の書き出しに時間の上限を設ける。

GPT-SoVITS のエンジンは合成の間、プロセスの作業フォルダを上流のフォルダへ移す。そのため、プロファイルの置き場所は起動時に絶対パスにしておく。

プロファイル ID (ペルソナ ID) は英数字に限らず受け付ける。2026-08 より前に作られた日本語のペルソナ ID が今も在籍しているため (今の外部サーバーは英数字以外の ID を断るので、そのペルソナは外部サーバーで声が出なかった)。英数字の ID はそのままフォルダ名にし (今の登録を引き継ぐため)、それ以外の ID は ID のハッシュをフォルダ名にして、元の ID を `profile.json` に残す。区切り文字・制御文字・前後の空白を含む ID と、128 文字を超える ID は断る。

参照音声は、内容のハッシュを名前に入れて保存する (今のサーバーと同じ)。エンジンは同じパスの参照音声を読み直さないので、差し替えたときにパスが変わる必要があるため。元の拡張子は残す。

### クライアント (外部サーバーへ依頼する側)

クライアント側 (remote_gpt_sovits.py) では、`protocol` を確かめてから依頼する。

- `/health` を読んで `protocol` が 2 以上なら、調整値と `"stream": true` を付けて依頼する。`protocol` が無い古いサーバーには今の形 (文章だけ・WAV 一括) で依頼し、「このサーバーでは調整値が効かない」とログに一度だけ残す。
- 確かめた結果は覚えておくが、合成が失敗したら忘れて、次の依頼の前に確かめ直す (同じ URL の向こうでサーバーが入れ替わっても追従するため)。`/health` 自体が読めなかったときは、その依頼を失敗として扱う。
- 調整値はペルソナの設定から送る。プロファイル ID として別に送る persona_id は、調整値からは外す。
- 応答は、別のスレッドで読み続けて受け取った順に溜める (今の子プロセスの読み方と同じ)。再生側は、先に作りすぎた声を抑えるために待つことがある。そのあいだクライアントが応答を読むのを止めると、サーバーは断片を送り出せずに止まり、その間ずっと順番を占めてしまう。だからクライアントは、再生側が待っている間も応答を読み続ける。
- 終了の通知を受け取るまでは成功とみなさない。途中で接続が切れたら失敗として扱う。
- ストリームでの再生に失敗したときに一文を作り直す経路 (一括の合成) でも、同じ調整値を付ける。
- タイムアウトの設定 (既定 15 秒) は、断片と断片のあいだの待ち時間の上限として効く。

### サーバーの起動

Voice TTS のフォルダに起動スクリプト (`serve.bat` / `serve.sh`) を置く。動き方は二通りある。

- **SAIVerse に Voice TTS を入れた機械**: スクリプトは SAIVerse のフォルダの Python (Voice TTS のフォルダから二つ上の `.venv`) を使う。Voice TTS を導入したときの Python と同じものでないと、エンジン専用の Python 環境を使えないため。SAIVerse のフォルダを読み込み先に足してから、子プロセスと同じ方法 (resolve_worker_python) でエンジン専用の Python 環境を探す。見つからなければ、SAIVerse の Python で黙って動かさず、理由を出して止まる (子プロセスの探し方は、見つからないと SAIVerse の Python に戻る作りなので、そのまま使うと、エンジンの入っていない Python でサーバーが動いてしまう)。サーバーには、子プロセスと同じ環境変数 (NLTK_DATA、HF_HOME など) を渡す。NLTK_DATA が無いと、英字の混じる文の合成が失敗する。
- **`--python <path>` を付けたとき**: SAIVerse を探さず、指定した Python でそのままサーバーを動かす。SAIVerse を入れていない機械で、手で作ったエンジンの環境を使う場合のため。このとき NLTK_DATA などの置き場所は、利用者の環境のものを使う。

共通の引数:

- `--engine gpt_sovits` (既定) / `--port 8082` (既定) / `--host`。`--host` の既定は `127.0.0.1` で、その PC の中からしか届かない。別の PC から使うには `--host 0.0.0.0` を明示する。
- `--data-dir` でプロファイルの置き場所を指定する。既定は、SAIVerse に入れた場合は SAIVerse のアドオン用データの置き場所 (`~/.saiverse/user_data/addon_data/saiverse-voice-tts/server/`)。アドオンのフォルダはアンインストールで消えるので、登録を残す場所にしない。`--python` で動かすときは `--data-dir` を必須にする。置き方は今の外部サーバーと同じ (`profiles/<id>/profile.json` と参照音声) にして、今の登録をそのまま引き継げるようにする。
- 使う GPU は、環境変数 `CUDA_VISIBLE_DEVICES` をスクリプトの前に設定して選ぶ。GPU が複数ある機械で、合成に使う GPU を固定するため。
- 認証は無い。LAN や Tailscale の中だけで使う前提で、README にそう書く。

サーバーは Python の標準ライブラリの HTTP サーバーで作る。エンジン専用の Python 環境に、Web の部品 (fastapi など) を足さずに済むため。GPT-SoVITS の環境には fastapi が入っているが、Irodori-TTS の環境では宣言されていない。

### 変えないこと

- ローカル合成のつなぎ方 (子プロセスと標準入出力)。ポートの管理が要らず、起動と後片付けが一番素直だから、という 2026-05-24 の決定 (docs/out_of_process.md) はそのまま有効。
- 外部サーバーの設定項目 (全体共通の URL、ペルソナ別の上書き URL、タイムアウト)。
- 今のクライアントへの応答の形。

### 合わせて直す文書

remote_gpt_sovits.md の「サーバーは完成 WAV を一括で返す」「送る合成引数はプロファイル ID とテキストだけ」は、この変更で成り立たなくなる。remote_gpt_sovits.md はこの文書に吸収し、ステータスを「この文書へ吸収」にして、その二つの記述をこの文書への参照に置き換える。ARCHITECTURE.md (remote_gpt_sovits.py の節)、README.md (外部サーバーの節)、remote_gpt_sovits.py の冒頭の説明も、同じ変更で直す。

## 守ること

- ローカルと外部で、同じ依頼 (文章・参照音声・書き起こし・調整値) から、同じエンジンのコードで声を作る。エンジンを回すコードは共通の合成関数の一箇所にだけ置く。言語などの機械ごとの設定は、その機械の設定ファイルに従う。
- 外部サーバーの拡張は足すだけにして、`protocol` を知らない今のクライアントへの応答は変えない。
- 新しいクライアントから古いサーバーへ依頼しても、今と同じ形で声が出る。
- 外部サーバーの声の断片は、ローカルと同じ形式で届き、同じ連結・保存・配信の経路に乗る。
- クライアントは応答を読み続け、再生側の待ちのせいでサーバーの順番を占め続けることがない。

## 今回やらないこと

- Irodori-TTS を外部サーバーで使う設定。共通の合成関数とサーバーは `--engine irodori` でも動く形にしておくが、設定画面の URL は GPT-SoVITS 用のままにする。
- SAIVerse を入れていない機械向けの自動導入。`--python` で手作りの環境を指せるところまでにする。
- サーバーの認証。

## 検証

テストでは、本物のモデルを使わず決まった音を返すテスト用のエンジンを使う。

1. 共通の合成関数をテスト用のエンジンで回し、子プロセスとサーバーが同じ声の断片を同じ順で返すことを確かめる。
2. テスト用のエンジンを持つサーバーを実際に localhost で起動し、HTTP 越しに次を確かめる: 古い形の依頼に WAV が返る / `stream` の依頼に声の断片が順に返る / 調整値がエンジンに届く / mp3 の参照音声を登録できる / 長さが範囲外の参照音声が 400 になる / 断片の前の失敗が状態コードで、途中の失敗がエラーの通知で返る / モデルの読み込み中は 503 になる / 切断で合成が止まり、次の依頼が通る。
3. 従来のクライアントと同じ依頼 (文章とプロファイル ID だけ) を新しいサーバーに送り、今と同じ WAV が返ることを確かめる。
4. 隔離した設定で、playback_worker → 外部サーバー (テスト用のエンジン) → 断片の連結 → WAV 保存まで通し、ローカルの子プロセスで同じ文章を通したときと同じ形で届くことを確かめる。再生側が待っている間もサーバーの書き出しが詰まらないことも確かめる。
5. 起動スクリプトを、SAIVerse を開発用の設定 (editable install) で入れていない、利用者と同じ状態の環境で動かし、エンジン専用の Python 環境を見つけてサーバーが起動することを確かめる。
6. 実機: 今動いている外部サーバーをこのサーバーに入れ替え、外部サーバーのペルソナが一言喋って、話速の設定が効き、最初の声が今より早く出ることを確かめる。入れ替えの前に、今の登録 (プロファイル) を新しい置き場所へ写し、待ち受けの `--host` と GPU の指定を今と同じにする。従来のクライアントの声も出ることを確かめる。

実機で確かめないこと: SAIVerse を入れていない機械での自動導入 (今回の範囲外)。

- 2026-10-12: 初稿の整合性の検査で、公開リポジトリに個人の PC 名と他の連携の名前が残っていたこと、登録の置き場所がアンインストールで消える場所だったこと、起動スクリプトが利用者の環境でだけ黙ってエンジンの無い Python で動く落とし穴、再生側の待ちでサーバーの順番が握られる問題、モデル読み込み中・切断・作業フォルダの移動の扱いが決まっていなかったことが分かり、反映した。
- 2026-10-13: 実機の GPU 機で、今まで動いていた外部サーバーをこのサーバーに入れ替えた (`--python` で既存のエンジンの環境を使い、今の登録は新しい置き場所へ写した)。見本の声のプロファイルで、従来の頼み方に WAV が返ること、ストリームで最初の声が 0.25 秒で届くこと、話速 1.4 で声の長さが 1.0 のときの 0.73 倍になることを確かめた。
